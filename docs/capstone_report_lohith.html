STRUCTURED ABSTRACT

Context: Modern real-time collaboration platforms (e.g., Zoom, Google Meet, Microsoft Teams) are architected around high-bandwidth multi-party video conferencing infrastructures that presuppose stable broadband connectivity (>1.5 Mbps) and high-tier client hardware. In rural, remote, and socio-economically marginalized civic environments across India, community organizations, public universities, and non-profit grassroots initiatives frequently operate under acute telecommunication constraints, characterized by 2G/3G cellular links, severe packet loss (>20%), high latency jitter (>300 ms), and low-cost low-memory mobile handsets.

Problem Formulation: Commercial and existing open-source WebRTC solutions fail catastrophically under extreme bandwidth deprivation. Full-mesh WebRTC topologies saturate upstream links on modest devices, while conventional Selective Forwarding Units (SFUs) force heavy client JavaScript bundles (>4 MB) and prioritize video packet transmission, triggering bufferbloat, continuous reconnection loops, and complete audio blackout. Furthermore, synchronous live streaming completely disenfranchises illiterate or semi-literate participants who depend on regional Indic languages (such as Telugu) and asynchronous conversational interfaces.

Proposed Architecture: This capstone project conceives, implements, and empirically validates Swecha Vedika, an ultra-bandwidth-frugal, multilingual live stage and asynchronous knowledge dissemination platform. Swecha Vedika introduces a triple-tier architectural paradigm: (1) an asymmetric 1:N Selective Forwarding Unit (SFU) media pipeline enforcing audio-first adaptive bitrate Opus encoding (RFC 6716) that drops packet consumption to 24–48 kbps under severe degradation; (2) an asynchronous WhatsApp conversational gateway powered by Baileys multi-device protocol and a finite-state machine (FSM), enabling users to submit stage questions and query archived knowledge without launching a web browser; and (3) an in-browser zero-server-cost multilingual transcription pipeline using Web Speech API with regional dialect adaptation.

Empirical Results: Systematic testbed evaluations utilizing Linux kernel traffic emulation (tc-netem) demonstrate that Swecha Vedika sustains uninterrupted audio transmission at 44.8 kbps with 35% artificial packet loss and 450 ms round-trip jitter, conditions under which commercial baselines completely crash or drop audio. The WhatsApp bot achieves a median response latency of 420 ms, and the entire server infrastructure runs stably on a single $6/month Linux droplet (1 vCPU, 1 GB RAM) supporting 120 concurrent listeners.

Keywords: Bandwidth-Frugal WebRTC, Selective Forwarding Unit (SFU), Audio-First Streaming, Indic Natural Language Processing, WhatsApp Conversational FSM, Rural Telecommunications, Digital Equity.

PROJECT CONTEXT, PROBLEM DEFINITION AND OBJECTIVES

1.1 Project Identity and Administrative Metadata

The capstone engineering project, formally titled "SWECHA VEDIKA: A BANDWIDTH-FRUGAL, MULTILINGUAL LIVE STAGE AND KNOWLEDGE PLATFORM," addresses the acute technical challenges of delivering real-time interactive voice communication, synchronous civic participation, and asynchronous knowledge preservation across resource-constrained, high-latency, and bandwidth-deprived environments. The project is undertaken under the domain of Blockchain & Cyber Security Systems by Team Y23-HTE KL-KLUG, within the Department of Experiential Learning and Global Engagement (EL&GE), Koneru Lakshmaiah Education Foundation (Deemed to be University), as part of the academic curriculum for the award of the degree of Bachelor of Technology (B.Tech) during the Academic Year 2026–2027.

Swecha Vedika was conceived in response to real-world deployment challenges identified during field interventions organized by the Swecha Telangana free and open-source software community. In rural learning centers, agricultural cooperative assemblies, and non-profit grassroots education initiatives across rural Andhra Pradesh and Telangana, existing proprietary communication tools consistently fail to provide reliable connectivity. This project represents a comprehensive systems-engineering response designed to deliver digital inclusion, linguistic equity, and open-access public knowledge infrastructure.

1.2 Problem Context and Grassroots Sociotechnical Provenance

The digital transformation of public education, community self-governance, and civil society assemblies has accelerated significantly in recent years. However, this transition has introduced profound structural inequities. The dominant commercial teleconferencing paradigm—epitomized by proprietary platforms such as Zoom, Google Meet, and Microsoft Teams—is fundamentally architected on assumptions of ubiquitous high-speed broadband infrastructure (>1.5 Mbps symmetrical throughput), low network jitter (<50 ms), negligible packet loss (<1%), and modern multi-core computing hardware.

In contrast, the reality of rural, remote, and socio-economically marginalized communities across the Global South, and particularly in rural India, is characterized by extreme telecommunication fragility. Field evaluations conducted across regional community learning centers reveal that rural connectivity relies almost exclusively on congested cellular towers operating under 2G, 3G, or severely throttled 4G connections. Available downstream throughput frequently drops below 50 kbps, uplink channels degrade to intermittent bursts, and round-trip ping times regularly exceed 400 to 600 ms.

When participants in these environments attempt to join conventional video-centric virtual meetings, the results are catastrophic. High client-side JavaScript execution footprints (>4 MB uncompressed bundles) overwhelm low-memory entry-level smartphones, precipitating browser crashes. Concurrently, video streams monopolize scarce network buffers, inducing massive bufferbloat, continuous media packet drops, and frequent connection timeouts. The participant is ultimately trapped in an endless reconnection loop, resulting in complete audio blackout and total exclusion from civic discourse.

1.3 Stakeholders and Operational Deployment Environment

The operating ecosystem of Swecha Vedika encompasses five primary stakeholder groups, each characterized by distinct operational constraints, technical literacies, and socio-economic realities:

  • Rural Students and Community Learners: Accessing sessions via low-cost Android smartphones operating on prepaid mobile data plans with strict daily limits. They require an ultra-lightweight client that functions seamlessly without demanding specialized application downloads or sustained high-bandwidth connections.
  • Civic Educators and Community Organizers: Conducting live instructional lectures, agricultural advisories, and civic literacy workshops. They require tools to deliver clear audio presentations, initiate real-time audience comprehension polls, and curate participant questions without technical friction.
  • Vernacular and Dialect Speakers: Participants whose primary language of comprehension is an Indic regional tongue (e.g., Telugu). They face severe language barriers on mainstream platforms that lack real-time local-language captioning and vernacular conversational interfaces.
  • WhatsApp-Centric Rural Citizens: Individuals who may lack modern web browser proficiency or high-speed data access but actively utilize WhatsApp for daily messaging. They require an asynchronous bridge that enables submitting stage queries and receiving synthesized audio summaries directly within their messaging environment.
  • Institutional and Civic Administrators: Open-source educational organizations, rural colleges, and non-profit entities operating under strict computational budgets who require self-hostable, low-maintenance infrastructure deployable on modest hardware.

1.4 Problem Statement and Primary Project Mandate

Existing digital meeting and live broadcasting platforms fail catastrophically under extreme rural network constraints (<100 kbps, >20% packet loss), enforce heavy client bundle overheads that crash low-cost smartphones, lack native vernacular Indic language transcription capabilities, and completely isolate synchronous live events from asynchronous offline community knowledge retrieval.

Therefore, the engineering mandate of this capstone project is: To design, architect, implement, and empirically validate an open-source, ultra-bandwidth-frugal live stage and knowledge dissemination platform (Swecha Vedika) that guarantees intelligible, low-latency audio transmission under 2G-level cellular constraints (sub-50 kbps), embeds zero-server-cost multilingual Indic speech transcription, integrates a bidirectional WhatsApp conversational finite-state machine, and enables compressed offline knowledge archiving deployable on a single budget cloud server.

1.5 Scope, Design Assumptions and Technical Boundaries

To ensure academic depth and practical feasibility, the architectural scope of Swecha Vedika is governed by rigorous system boundaries:

  • Architectural Scope: Swecha Vedika focuses on an asymmetric 1:N Broadcast and Curated Participation topology rather than an N:N video conference. The speaker's audio and optional lightweight visual cues are routed to many audience members, optimizing upstream bandwidth.
  • Audio-First Primacy: Audio packets are treated as first-class, inviolable network citizens. Video is treated as an optional secondary artifact that is dynamically throttled or dropped entirely when packet loss exceeds threshold limits.
  • Client Hardware Independence: The web client is built with zero heavyweight frontend frameworks, avoiding React/Angular overhead. The total page weight is strictly constrained to under 150 KB, ensuring rapid execution on low-memory mobile browsers.
  • Conversational Boundary: WhatsApp connectivity is implemented utilizing the open-source Baileys multi-device protocol, eliminating reliance on costly commercial enterprise BSP APIs while maintaining direct, bidirectional stage synchronization.
  • Security Boundary: All real-time media streams are secured using Datagram Transport Layer Security (DTLS) and Secure Real-time Transport Protocol (SRTP). Signaling channels are secured via TLS 1.3 WebSockets.

2.4 Low-Bandwidth Speech Coding Standards and Opus RFC 6716

The IETF standardized Opus interactive audio codec (RFC 6716) provides unprecedented flexibility by unifying Skype's SILK codec (optimized for human speech) and Xiph.Org's CELT codec (optimized for ultra-low latency music). Academic studies by Valin et al. demonstrate that Opus operating in SILK mode delivers superior speech intelligibility (PESQ > 3.4) at 16–24 kbps compared to legacy narrowband codecs (G.711, AMR-NB). Swecha Vedika exploits this capability by programmatically constraining Opus to narrowband/wideband speech modes under adverse network conditions.

2.5 Multilingual Transcription Paradigms and Indic NLP Pipelines

State-of-the-art Automatic Speech Recognition (ASR) pipelines for Indic languages (e.g., Whisper, AI4Bharat's IndicWav2Vec) require dedicated server-side GPU acceleration (NVIDIA T4/A100) to achieve real-time streaming inference. SYSTEM ARCHITECTURE, DATA DESIGN AND ENGINEERING DECISIONS

4.1 Architecture Alternatives and C4 System Context Model

The architectural formulation of Swecha Vedika is grounded in the C4 model for visualizing software architecture. At the System Context level (Level 1), Swecha Vedika serves as a centralized, bandwidth-frugal real-time collaboration hub interconnecting five external entity classes: Web-based Speakers, Web-based Rural Listeners, WhatsApp Mobile Participants, Civic Administrators, and External Speech Synthesis APIs.

Three foundational topological paradigms were evaluated during early architectural explorations:

  • Full-Mesh P2P Topology: Each client establishes bidirectional DTLS-SRTP peer connections with every other client. In a session with N participants, total network links scale as O(N^2), requiring each client to upload N-1 audio/video streams. This topology instantly collapses client uplink channels when N > 4, rendering it entirely unusable for broadcast sessions.
  • Multipoint Control Unit (MCU): A centralized server decodes, mixes, composites, and re-encodes all incoming participant streams into a single composite downlink stream. While bandwidth-efficient for clients (O(1) download), MCU mixing introduces massive server-side transcoding latency (>300 ms) and requires heavy multi-core CPU/GPU hardware, violating the low-cost self-hosting mandate.
  • Selective Forwarding Unit (SFU) - Selected Architecture: A routing server that receives media streams from publishers, inspects packet headers without decoding or re-encoding media payloads, and selectively routes packets to authorized subscribers. Client upload overhead remains O(1), downlink streams scale as O(K) where K is active speakers (K=1 in our stage paradigm), and server CPU utilization remains exceptionally low, perfectly satisfying the $6/month hosting constraint.

4.2 C4 Container and Component Decompositions

At the Container Level (Level 2), Swecha Vedika is decomposed into four decoupled, containerized services orchestrated via Docker:

  • Asymmetric WebRTC Media SFU (C1): C++ / Python asyncio signaling engine managing SDP negotiations, ICE candidate traversal, and selective forwarding of RTP audio packets.
  • Core Application & Signaling Service (C2): Asynchronous FastAPI service orchestrating session lifecycles, user authentication, Q&A message queues, instant poll tallies, and RESTful administrative interfaces.
  • WhatsApp Conversational Gateway (C3): Node.js daemon executing the Baileys multi-device socket protocol, managing session cryptographic credentials, parsing incoming conversational commands, and relaying stage events via HTTP webhooks.
  • Persistence and Caching Store (C4): PostgreSQL 15 relational database storing durable business entities, paired with an in-memory Redis 7 cache for sub-millisecond pub/sub signaling and active listener presence tracking.

4.3 Media Routing Model: Asymmetric 1:N SFU vs MCU Mixing

Swecha Vedika enforces an asymmetric 1:N stage broadcasting topology. Unlike symmetric multi-party conference rooms where all participants publish audio/video, Swecha Vedika designates a single active stage speaker (or panelist) as the publisher (N_pub = 1). All audience members connect as passive subscribers (N_sub ≥ 100). Audience participation is mediated through low-bandwidth data channels (text Q&A, poll votes) or explicit "raise hand" requests where the host promotes a listener to a temporary publishing role. This design eliminates upstream bandwidth contention on rural listener devices.

4.4 Mathematical Degradation Models and Opus Bit-rate Adaptation

To ensure uninterrupted speech intelligibility under erratic cellular bandwidth fluctuations, Swecha Vedika introduces a deterministic mathematical adaptation algorithm governing Opus codec parameterization. The target transmission bitrate R_target(t) at time interval t is calculated dynamically based on measured Round-Trip Time (RTT) and moving-average Packet Loss Rate (PLR):

R_target(t) = max( R_min, R_base × (1 - α × PLR(t)) × (1 - β × (RTT(t) - RTT_base) / RTT_max) ) (Equation 4.1)

Where R_base = 64 kbps, R_min = 24 kbps, α = 1.25, β = 0.40, RTT_base = 80 ms, and RTT_max = 800 ms. When PLR(t) > 0.20 (20% packet loss), the client automatically activates In-Band Forward Error Correction (FEC) and extends the packet frame duration from 20 ms to 40 ms or 60 ms:

T_frame(PLR) = [ 20 ms if PLR < 0.10;   40 ms if 0.10 ≤ PLR < 0.25;   60 ms if PLR ≥ 0.25 ] (Equation 4.2)

Extending frame duration reduces packetization protocol overhead (IP/UDP/RTP headers consume 40 bytes per packet; transmitting at 60 ms instead of 20 ms cuts packet header bandwidth by 66.7%). Furthermore, the buffer queuing delay D_q in the client playout jitter buffer is modeled using an exponentially weighted moving average (EWMA):

J(t) = (1 - γ) × J(t-1) + γ × |D_i - D_{i-1}| (Equation 4.3)
D_q(t) = min( D_max, μ_RTT(t) + 3 × J(t) ) (Equation 4.4)

Where γ = 0.125 and D_max = 450 ms. This adaptive jitter buffer guarantees glitch-free audio playback even during severe packet arrival jitter bursts.

4.6 WhatsApp Conversational FSM Architecture and Webhook Transitions

The WhatsApp conversational gateway operates as a deterministic Finite State Machine (FSM). When an incoming message arrives from the Baileys multi-device socket, the message is dispatched to the FSM handler:

  • STATE 0 (IDLE): Listens for trigger keywords. If user sends !stage, transitions to STATE 1; if !ask <msg>, transitions to STATE 2; if !vote <opt>, transitions to STATE 3; if !summary, transitions to STATE 4.
  • STATE 1 (DISCOVERY): Queries /api/stages/active via internal HTTP REST call. Formats stage title, host, and live listener count into a compact WhatsApp text template and replies to user.
  • STATE 2 (QUESTION RELAY): Extracts question payload, validates character length (10–300 chars), sanitizes text, and dispatches POST request to /api/stages/{id}/questions. The question is immediately broadcast to the live stage sidebar via WebSockets.
  • STATE 3 (POLL VOTING): Validates selected option against active stage poll ID stored in Redis session cache. Records vote in database and returns confirmation receipt to WhatsApp user.
  • STATE 4 (SUMMARY DELIVERY): Fetches compiled session micro-podcast audio file from storage and dispatches it as an audio message attachment directly within WhatsApp.

4.7 In-Browser Zero-Server-Cost Multilingual Transcription Pipeline

Rather than routing audio streams to high-cost cloud speech-to-text APIs (e.g., Google Cloud Speech, OpenAI Whisper), Swecha Vedika leverages the client's local browser runtime via the W3C Web Speech API (SpeechRecognition). When the stage host initiates broadcasting, the browser initializes a local recognition context bound to the session's target language (e.g., te-IN for Telugu, hi-IN for Hindi, en-IN for Indian English).

Acoustic speech frames captured by the browser microphone are decoded locally on the speaker's machine using built-in OS/browser acoustic models. As recognized text tokens are emitted, lightweight JSON payloads containing the transcript string, timestamp, and confidence score are pushed to the signaling server via WebSocket. The signaling server broadcasts these lightweight text frames (< 100 bytes each) to all connected listeners, who render live captions in real time with near-zero network and server compute overhead.
